git & GitHub

What are they?

git

  • a version control system
  • lives on your computer and keeps track of files and all changes made to them that you register with commits

GitHub

  • an online host for commits of code and data
  • lives on the internet

git & GitHub

Why are they important?

Backup: Easy way to upload files and add notes about changes. Excellent way to keep all your R work backed-up on the cloud

. . .

Version Control: Complete history of all changes and why they were made, and multiple branches of history

. . .

Open Access: Open, transparent, and public science. Some journals allow GitHub sites to be used to host data and code to meet their open-access requirements

. . .

Visibility: GitHub makes it easy to make your open-access work visible to people who might be interested (collaborators, employers)

. . .

Collaborative tool: Git and GitHub are designed for collaboration (even if you’re the only one coding). Easy to share files between collaborators, allows for merging work and reconciling conflicts.

. . .

Job Skill: This is an important data science skill

git & GitHub

How?

  1. Install git
  2. Create a GitHub account (hopefully you all have done this)
  3. Get a GUI and/or learn the command-line tools
    • I’m okay with either or both, as long as you (sort of) know what you’re doing
    • We’re going to use GitKraken in this course
  4. Develop a solid understanding of the underlying structure, so you know what you want to do even if you don’t know how
    • commits, push, pull, fork

git can be frustrating, but…

It is transparent – mistakes and all

Can be a powerful tool for collaboration

  • Communication between team members is important
  • Try to avoid merge conflicts
    • One person working on one thing at a time
    • Pull first each and every time!
    • Push often/at logical points

Excellent for reproducibility (a tenet of the data science pipeline)

  • Open data and code
  • Transparent
  • Forking paths

Open & Reproducible Research

  • Use scripting
  • Use dynamic documents
    • Quarto is fantastic
  • Use Git/GitHub
  • Use open data whenever possible
    • Consider ways you can make portions of the data open, if not all of it
  • Advanced – use tools that store software versions
    • {renv} (Rstudio)

Ignoring files

  • When we created the .Rproj the repo, we started it with a .gitignore file
  • The .gitignore file tells the repo not to track certain files
    • e.g., proprietary data
  • Not that important for now, but if you need to ignore a file in your repo for whatever reason, just put the name of the file(s) at the top of the .gitignore file
  • Or, create a folder in your .Rproj (e..g, nopublish) and put all your documents to be ignored in that file
    • then on the first line of your .gitignore file, type: nopublish/

Live Merge Conflict

Let’s give this a shot

Merge Conflict Activity (15 mins)

  1. Pair up: decide who is Partner 1 (P1) and Partner 2 (P2)
  2. P1: create a conflicted.qmd file in your repo from today
  3. P1: add P2 as a collaborator
  4. P2: accept the invite and clone the repo (then STOP, nobody edits yet)
  5. P1: edit the target line, commit, push
  6. P2: edit the same line differently, commit (don’t pull!)
  7. P2: try to push (it gets rejected)
  8. P2: pull (this creates the conflict)
  9. P2: open the file and inspect the weird markers
  10. P2: resolve the conflict in GitKraken
  11. P2: commit and push; P1 pulls to confirm

The Rules for Today

ImportantConflicts only happen when…

Both people change the same line with different text, and the second person tries to combine their work after the first person has pushed.

  • Follow the exact text I give you
  • Follow the order of the steps
  • Don’t pull or “fix” anything early

Step 1: Pair Up

  • Find a partner
  • Decide who is Partner 1 (P1) and who is Partner 2 (P2)
  • Sit next to each other so you can coordinate timing
Note

You will switch back and forth between working alone and waiting on your partner. Talk to each other!

Step 2: P1: create a conflicted.qmd

P1: create a new .qmd file and paste in the text below

Save it as conflicted.qmd in your repo from today

stage/committ/push!

---
title: "Merge Conflict Practice"
format: html
---

## Team Info

Favorite programming language: ______

Favorite snack while coding: ______

## Notes

This is the last line of the file.

Step 3: P1 Adds P2 as a Collaborator

P1 only:

  1. Go to your repo on GitHub
  2. Click Settings → Collaborators
  3. Click Add people
  4. Enter P2’s GitHub username and send the invite

Step 4: P2 Accepts and Clones

P2 only:

  1. Accept the invitation (check your email or github.com/notifications)
  2. In GitKraken: File → Clone Repo
  3. Choose the repo and a local folder, then click Clone
    • just save it to your desktop
  4. Confirm you see conflicted.qmd
WarningSTOP!

Nobody edits anything until both partners have cloned and confirmed.

Step 5: P1 Edits, Commits, Pushes

P1 only: Open conflicted.qmd and change this line:

Before

Favorite programming language: ______

After

Favorite programming language: R

Then in GitKraken:

  1. stage the file
  2. commit with message: P1 favorite language
  3. push and wait for it to succeed

Step 6: P2 Edits the Same Line

P2 only: After P1 has pushed, open conflicted.qmd and change the same line:

Favorite programming language: Python
  1. stage the file
  2. commit with message: P2 favorite language
WarningDo NOT pull or fetch yet!

GitKraken may show you are “behind” by 1 commit. That’s expected. Ignore it for now.

Step 7: P2 Tries to Push

P2: Click push.

. . .

What happens? The push is rejected.

. . .

Why?

  • P1’s commit is already on GitHub
  • Your commit is only on your computer
  • Your histories have diverged, and Git won’t overwrite your partner’s work

Step 8: P2 Pulls to Trigger the Conflict

P2: Click Pull in GitKraken (choose Pull (merge) if asked).

. . .

Expected result: GitKraken reports a merge conflict and conflicted.qmd appears as conflicted

NoteNo conflict?

Check that you both edited the same line with different text. Raise your hand if you’re stuck!

Step 9: Look at the Damage

P2: Open conflicted.qmd in a text editor (not GitKraken). You should see:

<<<<<<< HEAD
Favorite programming language: Python
=======
Favorite programming language: R
>>>>>>> origin/main

Discuss with your partner:

  • Which section is your version?
  • Which section is your partner’s?
  • What do <<<<<<<, =======, and >>>>>>> mark?

Decoding the Markers

<<<<<<< HEAD                          ← start of YOUR (local) version
Favorite programming language: Python
=======                               ← divider
Favorite programming language: R      ← your PARTNER'S (remote) version
>>>>>>> origin/main                   ← end of conflict
  • Git can’t decide which line is correct, so it asks you
  • These markers are not valid content, and they must be removed

Step 10: Resolve in GitKraken

P2:

  1. In GitKraken, click the conflicted file in the Unstaged / Conflicted Files panel
  2. The conflict resolution view opens
  3. Check the box for P1’s line, P2’s line, or both
  4. Or edit the output pane yourself, for example:
Favorite programming language: R, NOT Python
  1. Confirm the output has no <<<<<<<, =======, or >>>>>>>

Step 11: Commit and Push the Resolution

P2:

  1. Click Save in the conflict view
  2. stage the resolved file
  3. commit (keep the pre-filled merge commit message)
  4. push

. . .

P1: Click ****pull**** and confirm you see the resolved line in your file.

Check the Commit Graph

Both partners: Look at the graph in GitKraken.

  • Can you spot where the history diverged?
  • Can you spot the merge commit where it came back together?

Stuck? Troubleshooting

Symptom Likely cause Fix
P2’s push succeeds P1 hadn’t pushed yet, or P2 pulled before committing Re-clone and redo steps 4 to 6 in order
Pull works, no conflict Different lines edited, or identical text typed Use the exact text on the slides
“Pull” is greyed out Uncommitted changes Commit first (Step 5)
Markers still in file Resolution not saved Re-open the conflict view, remove markers, Save

Discussion Questions

  1. Why did Git reject P2’s push?
  2. Why couldn’t Git resolve this conflict automatically?
  3. What would have happened if you had edited different lines?
  4. How can teams avoid conflicts in real projects?
